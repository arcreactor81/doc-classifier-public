# Correction proposals

`proposeCorrections` consumes the immutable `diffCorrection` result, per-tag recorded certainty/agreed type/title/digest lines, the current threshold, an explicit minimum filed count, project type names, explicit unknown-folder decisions and a central-copy callback for candidate `not_for` sentences. It returns structured counts, threshold proposals carrying correction identity and evidence tags, example candidates, pair-based `not_for` candidates, incomplete new-type stubs and every move. It performs no persistence or automatic application.

A filed check includes checked-folder R1 confirmations and every explicit R1 move, even when its source folder was not checked. Unchecked unmoved, deleted, ignored and unresolved-folder documents are excluded. Both threshold directions are withheld below the configured minimum filed evidence (initial 50). Counts remain visible.

A raise is proposed only when every wrong certainty is strictly below every correct certainty; it uses the lowest correct certainty, which retains correct labels under the >= rule. Equal or overlapping certainties cannot separate. No arbitrary epsilon or threshold grid is used. A lower proposal uses explicit R2 human labels only, chooses the lowest observed agreeing certainty below the current threshold with zero observed errors at or above that candidate, and reports the additional labels below the current threshold. An unmoved review document supplies no type label. These are observations of the corrected set, not guarantees for future documents.

Unknown folders stay unresolved until explicitly marked ignore/new_type. New stubs retain the exact folder name and placed examples, leave what/not_for empty, and suggest an ASCII snake_case ID. Empty, reserved or colliding ID suggestions become null for human completion; the correction itself is untouched. Candidate examples preserve supplied title/digest content. Every edit remains a proposal. In the maintained runtime-definition flow, an authorized editor reviews a complete draft and explicitly activates a new category revision in the website; Git remains the seed/legacy definition path. Only a separate explicit Apply operation may persist a threshold with its correction justification and revision checks.

`carryTrialChecks` (`carry.ts`; owner decision of 6 October 2026, DECISIONS 133 (e)) carries the trial's checks into the full run's correction comparison. A document the person marked right in the trial, which the full run filed (R1) into the same folder again and whose copy is still in that folder, moves from unchecked to confirmations, exactly as if its folder had been ticked; the filed check, the examples and the reference candidates then treat it as confirmed. A document already confirmed or moved is left alone, so nothing is counted twice. It is pure: it returns the carried tags so the review can list them, and it never changes a threshold, applies a category or edits what the person submitted.

Processing failures may still receive human labels. Their proposal evidence carries certainty:null and agreedType:null, plus the available title/digest metadata. Such records can produce example candidates without a model output. Threshold analysis for original R1/R2 decisions continues to require recorded numeric certainty; null is never coerced to zero or inferred from a human move.
