# Jev decision guidance review

Checked **4 November 2026** against current first-party TypeSafe documentation and its current official agent skill. Scope: `core/vendors/requests.ts`, confidence transport/context policy, and the prepared decision-only comparison. This review changes no production code, request, input, threshold, sample or scoring rule, and makes no model calls.

## Finding

The existing Jev request is compatible with the current native API and already follows its central practices: named structured state, explicit field references, structured category definitions, one Choice plus independent per-category Nouls in a single request, raw response retention, exact version checking, and decisions in code. No discovered syntax incompatibility justifies rewriting the Jev baseline before comparison. Several current recommendations are worthwhile **experiments**, but would change what a model sees or how its output is used; they are proposals for the owner, not repairs to apply silently.

## What is already sound

- **State and references.** `confidenceRequestParts` parses the stored JSON into a native state object; it does not send serialized JSON as an opaque text field. Current instructions explicitly reference `fullText`, `title`, `headings` and `tables`. The Noul places its definition inside that question, so it does not depend on the model seeing the `is_<id>` key or another question. Question IDs are not model-visible; meaningful Choice option names are. Sources: [state](https://docs.typesafe.ai/concepts/state), [primitives](https://docs.typesafe.ai/primitives), [building guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md).
- **Criteria shape.** Choice option objects carry the same `name`, `what`, `not_for` and `examples` structure. Noul true/false criteria and structured instructions are supported natively; flattening them to accommodate another provider is not necessary for Jev. Positive Noul means category membership, not intensity, and no separate Noul confidence is required. Source: [advanced structure](https://docs.typesafe.ai/primitives/advanced).
- **Parallel composition.** Choice and Nouls share one complete state and are answered independently. A Noul cannot see the Choice result, and it must not be phrased as though it can. The current membership question does not rely on such a result. State is ingested and paid for once per request; extra question tokens are still charged. Splitting into several requests repeats state billing. Sources: [parallel questions cookbook](https://docs.typesafe.ai/cookbooks/parallel_questions.md), [speculative fan-out](https://docs.typesafe.ai/patterns/fan-out), [System One API](https://docs.typesafe.ai/api/system-one).
- **Transport and money.** The production adapter freezes body and selected context policy, retains raw answers before parsing, validates model identity, bounds attempts and honors `retry-after`. The offline comparison records one attempt and has no executor. Generic SDK retry recommendations do not override those narrower experiment and spending rules. Missing usage remains unknown; a documented transient status does not itself prove the call was free. Sources: [request rules/errors](https://docs.typesafe.ai/api/errors), [API usage fields](https://docs.typesafe.ai/api/system-one).

## Context, versions and what the experiment isolates

TypeSafe currently publishes standard limits of 32k tokens for state plus any single question and 64k for state plus all questions. Both Jev 1.13 and 1.14 support an explicit `TypeSafe-Danger-Zone-Long-Context: true` header raising both to 262k. Output is free; input is USD 0.042 per million tokens. There is no separate question-count cap, while Choice permits up to 255 options. The long mode is described as slower and less accurate, so capacity is not an accuracy guarantee. Source: [models and limits](https://docs.typesafe.ai/models).

The implementation's explicit frozen opt-in and unchanged retries are sound. Do not turn a standard failure into a changed-request retry with long context, and do not silently pick a shorter document representation. The owner's earlier 262000 integer interpretation is recorded in DESIGN; public “262k” prose alone does not prove a measured exact acceptance boundary. The new separate category-question allocation is planning, not a document tokenizer.

The prepared arms isolate two effects: Jev 1.13 standard versus 1.14 standard is a version comparison; 1.14 standard versus 1.14 long is a context-policy comparison. Report coverage of all scheduled cases as well as accuracy on common valid cases. Comparing only accepted standard requests would conceal the long arm's size coverage, while treating failures as ordinary wrong labels would conflate service capacity with classification. Do not claim this directly measures the separately configured production 1.13-long setting. Pin exact version IDs and check the returned version; the moving aliases in documentation examples are not appropriate here.

## Guidance that must not be imported as an automatic product change

The current skill prefers shorter, directly named judgments and concrete contrasts. Its advice to decompose broad judgments can motivate a new semantic-feature design, but this product's current observable contract is category membership, not a newly invented weighted classifier. The guide's examples of combining signals, changing thresholds, filtering state, or using model-generated labels are not authorization to combine Choice and Noul arithmetically, shorten documents, replace human/reference labels, or add an LLM to this decision-only study.

The older [classification-with-confidence cookbook](https://docs.typesafe.ai/cookbooks/classification_using_confidence.md) is a useful workflow example, not a current calibration guarantee. It reports Jev 1.12 on a selected set of short sections, with self-reported labels screened against their text. Its prose also claims different runner-up distributions distinguish confidence at the same top probability; that contradicts the current confidence reference, where only `p_max` and option count determine Choice confidence. Use the current reference for semantics and retained raw responses for observed behavior, not that historical example to justify this corpus's threshold.

The current [official skill](https://raw.githubusercontent.com/typesafe-ai/skills/main/skills/typesafe-ai/SKILL.md) has materially changed from the local root `SKILL.md`: stronger advice on false rubrics, null-case Nouls, and treating confidence as distribution concentration. It remains guidance subject to the user's design. No skill installation or local skill replacement was performed. The [agent-skill page](https://docs.typesafe.ai/agent-skill) links this official source and emphasizes review of questions and constants.

## Smallest useful next decision

Keep the frozen baseline as the first comparison. Present the owner with one optional **generic contrastive Noul-rubric variant** before implementing it; separately ask whether an **any-fit control** is worth adding given the absence of out-of-taxonomy reference cases. Do not bundle those with model migration, context changes or an altered threshold. If authorized, freeze the exact questions, preserve a holdout untouched by wording selection, and report per-group results with failures and denominators. Repeated calls, order checks and adversarial controls consume the same expressly bounded campaign allowance; none were run here.
