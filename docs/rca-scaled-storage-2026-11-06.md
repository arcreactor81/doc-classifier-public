# RCA: scaled test stopped during batch 15

Investigation date: 6 November 2026 IST. Incident: approximately **01:49:09 IST on 6 November** (`2026-11-05T20:19:09Z`). This is a read-only investigation; no model call, failed-request replay, data correction, Access change or runtime code change was made for the RCA.

## Conclusion

**Confirmed immediate cause:** Cloudflare D1 rejected database operations with `D1 DB is overloaded. Too many resources consumed within a 10 second window`.

**Strongly evidenced workload contributor:** repeated daily-spending calculations rescan retained reservation history during concurrent document execution. In the captured 11-second window, four accounting query forms account for approximately 99.48% of recorded rows read and 77.42% of recorded SQL execution time. The live query planner confirms that the reservation side uses only the pool prefix of its `(pool, day)` index.

**Failure-amplification and recovery gap:** saving a stage failure and halting the run require the same database that was rejecting requests. Overload is deliberately excluded from the retryable-error list. The halt attempts failed once, Workflow execution terminated, and D1 retained stale running states. The ordinary polling path cannot display a halt that was never recorded.

This was not demonstrated to be a model error, context refusal, budget exhaustion or sign-in failure. Sign-in expired separately and obstructed later inspection. The exact Cloudflare CPU/memory threshold and the relative contribution of memory versus CPU are not exposed by the captured evidence; do not invent a numeric capacity limit or claim that concurrency alone is the cause.

## Evidence chain

1. The runner received HTTP 500 `E_INTERNAL` from `GET /api/runs` at `20:19:10.238Z`, stopped and did not create batch 16.
2. Historical Workers telemetry contains **54 D1 overload error spans** in the inspected `20:19:07Z–20:19:12Z` window. The earliest returned span starts at `20:19:09.679Z`. Failed operations include guards, checkpoint persistence, document links, run completion, status reads and the halt transaction itself. These are independent of the generic error message shown to the runner.
3. A halt-transaction span at `20:19:09.917Z` shows the database rejecting `UPDATE runs SET status='halted' ...` and its event insertion with the same overload error. Application logs show `run_halt`, `outcome: failed`, `attempts: 1`.
4. All 50 native instances created for the partial batch were inspected: 28 complete and 22 errored, with no executing instance. The failures cluster around `20:19:09Z`. D1 retains 29 decisions, because one instance failed after saving its decision. Ten uploaded documents have no native instance. D1 remains authoritative for outcomes.
5. The run row still says running and has no halt record. One Jev reservation lacks a settled call or cancellation. Native terminal status does not justify deleting that reservation, assigning zero usage, or rewriting decisions.

Cloudflare's [D1 debugging documentation](https://developers.cloudflare.com/d1/observability/debug-d1/) explicitly identifies this error as database rate limiting after excessive CPU and memory consumption over ten seconds, with repeated scans, slow queries and large responses as possible contributors. This differs from queue-length overload and from a database-size limit.

The aggregation returned 45 SQL shapes, 2,786 recorded calls, 1,773,542 rows read, and 3,036.63 ms of SQL execution. These are observed telemetry totals, not the undocumented rate-limit accounting formula. This diagnostic window is 11 seconds, not a claim to identify Cloudflare's exact rolling window.

The accounting SELECT text generated by the current source matches the observed SQL lengths. The two model-pool entries are grouped by SQL shape; the telemetry does not expose bound values, so the aggregate alone cannot attribute every invocation to one model pool.

`core/server/daily-usage.ts` calculates usage before reservation admission and on other guard/reconciliation paths. Its reservation branch has:

```sql
WHERE r.pool=? AND (r.day=? OR (v.created_at>=? AND v.created_at<?))
```

The live, read-only `EXPLAIN QUERY PLAN` for both Jev and the paid OpenAI pool reports:

```text
SEARCH r USING INDEX daily_usage_pool_day (pool=?)
SEARCH v USING INDEX sqlite_autoindex_vendor_calls_1 (attempt_id=?) LEFT-JOIN
```

The cross-table OR preserves necessary cross-day settlement semantics, but prevents narrowing the reservation index by day on this branch. Each matching pool's history is visited before the date condition can be resolved. Jev has 4,772 retained reservations, of which 881 are on the incident day. The paid OpenAI pool has 940, all on that day. The vendor table has 9,683 calls in total, of which 1,820 are on the incident day. These counts were read after the incident; they support the query-plan diagnosis without claiming an exact memory-allocation measurement.

The second vendor branch already uses a date index for Jev and the model/date index for OpenAI. It is incorrect to say that all indexes are missing or that the entire database is scanned by every query.

The execution guard is a secondary cost: 995 calls in the captured window, each requesting the full run row. This run's frozen pack contains 14,760 characters. Narrowing the guard's projection deserves inspection, but its correctness checks must remain and the RCA does not establish this as the primary trigger.

## Why the application did not save a stop

`core/server/d1-write-policy.ts` intentionally retries a short allowlist of transient network/reset messages. Overload, limits and timeouts are explicitly excluded. `persistLifecycle` in `core/server/run-persistence.ts` sees the overload as non-retryable, logs a failed halt, and throws `E_RUN_STATE`. `Store.halt` reconciles spending only after an owned, persisted halt transition. This explains why neither the halted state nor its subsequent reconciliation was recorded.

The inspected confidence workflow failed while trying to confirm its stage failure, then failed again while persisting the run halt. This created a terminal native instance with a running D1 checkpoint and a pending reservation. It does **not** establish whether a vendor accepted that attempt. Clearing or replaying it would require evidence the investigation does not yet have.

The app's behavior is fail-closed for those invocations, but its durable failure-reporting path has a gap under database-wide overload. Already-running peers can still retain outcomes after the brief overload ends because the shared halt never committed. The 29 retained outcomes are preserved as recorded; this RCA does not alter or suppress them.

## Why existing tests did not prevent it

The deployment gate proved functional behavior on local synthetic databases. It did not establish live D1 capacity under a growing retained ledger and this concurrent workload. The daily-usage tests exercise arithmetic, atomic admission, unknown usage and cancellation; they are not a historical-ledger performance benchmark. Passing 2,881 tests and 2,320 local acceptance checks is therefore compatible with this production overload. The acceptance claim should remain scoped accordingly.

## Repair sequence and required proof

1. **Optimize the accounting SQL without weakening admission.** Split current-day reservations from earlier reservations settled today using disjoint, indexable branches. Preserve cross-day conservative charging, cancellation ownership, unknown costs, model/run identity checks, overrun detection and the atomic reservation INSERT. Do not replace the guard with a stale cached total or delete history.
2. **Add a realistic ledger regression benchmark.** Use retained-history scale and concurrent admission in a local fixture. Compare old/new results exactly across units, pools, midnight, late settlement, cancellation and unknown-usage cases. Capture query plans and rows visited; correctness and a material reduction must both be demonstrated. No live model calls are needed for this proof.
3. **Specify durable overload settlement.** After a transient overload has cleared, a narrowly bounded control operation must be able to record the original stop and reconcile factual state without repeating a model request. Blindly adding overload to the general retry allowlist would amplify load and is not the proposed fix. Any new recovery policy needs an explicit design record and failure-injection tests for lost writes and readbacks.
4. **Reduce avoidable coordination reads and bound dispatch pressure if measurements still require it.** Evaluate the full-row execution guard and overlapping status polling. Preserve kill/stop checks and request content. Do not guess a safe document count from one failure, add autoscaling, or change classification inputs for throughput.
5. **Add a supported path for this missing interruption record.** After renewed sign-in, authenticated health reads returned READY and confirmed the USD 1 Jev limit. One call to the existing run-scoped runtime observer returned `checked: 0, failed: 0`; it selects already-recorded pending interruptions, and there is none for it to settle here. The run remains stale-running with 29 decisions and one pending accounting item. A non-destructive run-specific repair must preserve those facts and avoid replay. The existing alternatives are a site-wide emergency stop or discarding the run; neither was used to conceal the recovery gap. No new paid test batch follows automatically.

These were the initial repair proposals. The subsequent [query-first rollout and native load validation](d1-load-validation-2026-11-06.md) shipped the indexed query and, after query-only overload was reproduced, measured start-rate pacing. The separate missing-halt/interruption-record recovery gap remains open; pacing is not represented as a repair of historical accounting.
